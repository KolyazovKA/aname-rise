# План устранения замечаний Ponytail Review

## 1. Цель

Устранить пять замечаний, обнаруженных при анализе репозитория `KolyazovKA/aname-rise`.

Изменения должны:

- сохранять существующее поведение приложения;
- сокращать ненужный код и аллокации;
- не добавлять новые зависимости;
- не менять архитектуру проекта;
- не затрагивать функциональность, не связанную с замечаниями.

Работать в текущей ветке, предварительно проверив `git status`. Не перезаписывать пользовательские изменения.

## 2. Этап 0. Проверка исходного состояния

Перед изменениями:

1. Получить актуальную версию репозитория.
2. Проверить текущую ветку и commit.
3. Проверить `git status`.
4. Изучить актуальные версии файлов:
   - `Cargo.toml`
   - `src/notifications.rs`
   - `src/state.rs`
5. Проверить, не были ли замечания уже исправлены.
6. Выполнить исходные проверки:
   - `cargo check`
   - `cargo test`

Если проект не собирается в исходном состоянии, зафиксировать существующие ошибки и не приписывать их будущим изменениям.

Приоритет: высокий.

Проблема:

В конфигурации обнаружены локальные пути, привязанные к машине разработчика:

`/home/krik/.config/amane/src/main.rs`

`/home/krik/.cache/amane/library`

Что сделать:

1. Проверить структуру проекта.
2. Проверить наличие `src/main.rs`.
3. Для бинарного target использовать стандартное расположение Rust:
   `src/main.rs`.
4. Проверить происхождение зависимости `amane`.
5. Если библиотека входит в репозиторий, использовать корректный относительный путь.
6. Если библиотека является внешней зависимостью, определить её источник и версию.
7. Не заменять локальную зависимость случайной версией из crates.io.
8. Удалить ненужное объявление `[[bin]]`, если стандартная конфигурация Cargo полностью заменяет его.

Ограничения:

- Не менять API библиотеки.
- Не обновлять зависимости без необходимости.
- Не менять `Cargo.lock` без объективной причины.
- Не удалять конфигурацию, если она необходима для специальной схемы сборки.

Критерии приёмки:

- В `Cargo.toml` отсутствуют абсолютные пути конкретной машины.
- Проект собирается в предусмотренном окружении.
- Путь к `amane` корректен и воспроизводим.
- Сборка не зависит от домашней директории разработчика.

## 4. Задача №2. Упростить расчёт translates в notifications.rs

Приоритет: средний.

Файл: `src/notifications.rs`

Текущий участок: строки около 397–411.

Проблема:

Создаётся отдельный вектор `translates`, который используется только для передачи вычисленных значений в цикл создания карточек.

Текущая логика:

1. Создание `Vec<f32>`.
2. Вычисление `clear_translate()` для каждого элемента.
3. Последующее получение значения по индексу.
4. Передача значения в `notif_card()`.

Что сделать:

1. Удалить промежуточный `Vec<f32>`.
2. Оставить один цикл по `entries.iter().rev().enumerate()`.
3. Внутри цикла вычислять:
   `NotificationHistory::clear_translate(index_from_end, clearing, elapsed_ms)`.
4. Передавать результат непосредственно в `notif_card()`.
5. Сохранить существующую логику индексации.

Важно:

`index_from_end` должен остаться равным `entries.len() - 1 - i`.

Нельзя случайно заменить его на `i`, поскольку это изменит порядок соответствия анимаций карточкам.

Критерии приёмки:

- Промежуточный `Vec<f32>` отсутствует.
- Результат `clear_translate()` соответствует прежним индексам.
- Порядок карточек не изменился.
- Анимация очистки уведомлений работает как раньше.

## 5. Задача №3. Убрать лишний clone в notifications.rs

Приоритет: низкий.

Файл: `src/notifications.rs`

Создаётся копия строки:

Что сделать:

1. Проверить все использования `key` после создания `k`.
2. Если исходная строка больше не нужна, переместить её непосредственно в closure.
3. Удалить промежуточную переменную `k`.
4. Сохранить поведение `Ui::set_hover()`.

Ожидаемый результат:

- Одна строка вместо двух.
- Отсутствие ненужного клонирования.
- Отсутствие изменения логики hover.

Критерии приёмки:

- `key.clone()` удалён.
- Обработчик hover продолжает работать.
- Нет ошибок владения и заимствования.

## 6. Задача №4. Упростить вычисление diff в state.rs

Приоритет: низкий.

Файл: `src/state.rs`

Текущий участок: около строки 252.

Проблема:

Вычисление:

`(now_secs + offset).saturating_sub(ts_secs + offset)`

Добавление одинакового часового смещения к обеим временным меткам не влияет на разницу.

Что сделать:

Заменить выражение на:

`now_secs.saturating_sub(ts_secs)`

Проверить:

- `now_secs` и `ts_secs` по-прежнему выражены в Unix timestamp.
- Смещение часового пояса продолжает использоваться при форматировании времени уведомления.
- Обработка будущих уведомлений остаётся прежней.
- Пороговые значения 60 и 3600 секунд не меняются.

Критерии приёмки:

- Вычисление разницы времени упрощено.
- Форматирование уведомлений не изменилось.
- Поведение при разнице меньше минуты, меньше часа и больше часа сохранено.

## 7. Задача №5. Убрать лишнюю аллокацию в state.rs

Приоритет: низкий.

Файл: `src/state.rs`

Текущий участок: около строки 441.

Проблема:

При перечислении сетевых интерфейсов создаётся дополнительный `String`:

`entry.file_name().to_string_lossy().to_string()`

Что сделать:

Использовать результат `to_string_lossy()` без дополнительного преобразования в `String`.

Например:

`let name = entry.file_name();`
`let name = name.to_string_lossy();`

Затем сохранить существующие проверки `starts_with()`.

Проверить:

- Работу с именами интерфейсов `happ`, `xray`, `wg`, `tailscale`, `ppp`, `proton`, `nordlynx`.
- Обработку интерфейсов `tun`.
- Исключение `tunl`.
- Отсутствие изменения поведения определения VPN.

Критерии приёмки:

- Лишний `to_string()` удалён.
- Проверки имён интерфейсов работают как раньше.
- Не создаются дополнительные промежуточные аллокации.

## 8. Этап 6. Проверка изменений

После реализации всех пяти задач:

1. Просмотреть `git diff`.
2. Проверить отсутствие изменений за пределами трёх целевых файлов.
3. Выполнить:
   - `cargo fmt --check`
   - `cargo check`
   - `cargo test`
4. Проверить отсутствие новых зависимостей.
5. Убедиться, что `Cargo.lock` изменён только при объективной необходимости.
6. Проверить, что не изменились публичные API и логика UI.
7. Проверить, что в diff нет случайных форматирующих изменений.

Если проект требует специфического окружения, отдельно указать, какие проверки не удалось выполнить.

## 10. Общие ограничения для AI-агента

СТРОГО ЗАПРЕЩЕНО:

1. Добавлять новые архитектурные слои.
2. Создавать новые менеджеры сервисов.
3. Переписывать модули целиком.
4. Добавлять зависимости ради небольших упрощений.
5. Менять визуальное оформление интерфейса.
6. Менять поведение уведомлений, VPN, сети и звука.
7. Проводить несвязанный рефакторинг.
8. Удалять существующие тесты.
9. Маскировать ошибки сборки.
10. Изменять пользовательские незакоммиченные изменения.

Главный принцип: исправить ровно пять замечаний с минимальным количеством изменений.

Если какое-либо изменение требует изменения поведения или существенного рефакторинга, остановиться и объяснить причину вместо самостоятельного расширения задачи.
